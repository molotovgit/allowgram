# Allowgram Head management — frozen v1 integration contract

> This is the initial design contract, not a claim that every acceptance gate is complete. The implemented temporary authentication uses separate one-time owner/head access codes; Telegram Login Widget/OIDC integration is **not implemented**. The native UI currently shows identity, pinned origin, revision and error state, but not a last-success timestamp. See README.md for current behavior and rollout limitations. The v1 enrollment, signed-policy and ACK wire formats below remain the integration contract.

Authorized goal: temporarily host a real head/admin dashboard on the Mac and build native live allowlist management. Preserve initial local chat-picker setup and all existing session/account data. No Sheets onboarding, Google credentials, roster import, production user import, real account reads, installed-app modification, public release/merge or Telegram bot configuration changes are authorized by this implementation brief. Old QA broker remains untouched. Use synthetic identities in tests. Initial real service is empty except owner principal 8683512953.

## Transport and identity
- HTTP JSON, client endpoints below; browser API may add its own CRUD routes. HTTPS origin in invitations, with no userinfo/query/fragment/path (optional trailing slash normalizes away). Never follow HTTP redirects while sending credentials. Production native client rejects plain HTTP; injectable test-only transport may use loopback in an isolated test target, never a production runtime bypass.
- Device enrollment is an explicit capability grant by owner/assigned head to a specific Telegram numeric user ID. Native client derives its ID from the authenticated Main::Session, not an editable input. Backend invitation/token is bound to that ID. Capability pairing is NOT claimed to independently verify Telegram's server-side authentication; do not label it Telegram SSO.
- Invitations are `AGH1.` plus unpadded base64url UTF8 JSON: {"v":1,"url":"https://host","telegram_user_id":"123","code":"<32+ random bytes base64url>","public_key":"<32 raw Ed25519 bytes base64url>"}. Single use, expires after 15min; show account/host before user confirms. Limit invitation input to8KiB; decimal IDs canonical, positive, <=281474976710655. Token/signing key never logged.
- Enrollment pins this dedicated management signing key. It is unrelated to software-update signing. Keys remain in a private data directory outside repo, permissions0600/0700. No hardcoded temporary tunnel hostname in compiled native code. Dashboard must describe temporary hosting and last-sync truthfully.

## Peer/policy data
- Peer: {"kind":"user"|"chat"|"channel","id":"canonical-positive-bare-decimal"}. ID <=281474976710655; no numeric JSON IDs/IEEE754 conversion. UI may supply an optional label<=128 chars (no control chars), stored/displayed as escaped metadata. Signed peers have only kind/id. Sorting deterministic by(kind,id); reject duplicates. Max10000 peers, policy JSON max1MiB. Empty managed list is valid deny-all, NOT unconfigured; initial onboarding remains unchanged.
- Per Telegram user, revision0 means never initialized, then strictly increasing integers 1..9007199254740991. Policy storage carries a persistent updated_at Unix seconds. First enrollment seeds from initial_peers only if revision0; subsequent devices/enrollments cannot overwrite an existing managed list. Head may preset a list before enrollment.
- Signed policy payload UTF8 JSON: {"v":1,"telegram_user_id":"123","device_id":"32-lowercase-hex","revision":1,"issued_at":<persistent policy updated_at integer>,"peers":[{"kind":"user","id":"456"}]}.
- Wire envelope: {"signed":"<base64url exact UTF8 payload bytes>","signature":"<base64url 64byte Ed25519 signature>"}. Signature is Ed25519 over ASCII `ALLOWGRAM_HEAD_POLICY_V1\n` concatenated with exact decoded payload bytes. Backend JSON serialization sort_keys=True,separators=(',',':'),ensure_ascii=False; client verifies raw bytes, NOT reserialized JSON. Per-device signed payload is stable for each policy revision. No policy expiry: explicitly retain last-known allowed list offline. Reject malformed/oversized/duplicate identity/security fields, wrongsubject/device, tamper, invalid peer IDs, future issued_at>5min; never roll revision backward or accept different bytes for same revision. Failed fetch/apply must not unlock or wipe cache.

## Native endpoint contract
1. POST /api/client/enroll
   Request {"code":"...","telegram_user_id":"123","initial_peers":[{kind,id,label?}],"device_name":"Allowgram Windows","client_version":"7.2.8.10-dev"}. Strict length limits, device_name<=100, version<=40. Atomic consume-and-create so replay/races cannot create a second device. Wrong ID MUST NOT consume a valid code.
   Response {"device_id":"32hex","device_token":"<32+ random bytes base64url>","policy":<signed envelope>}. Token hash only in SQLite; per-device credentials. Losing an enrollment response may require a newly issued invitation; never reuse/return plaintext stored tokens.
2. GET /api/client/policy with Authorization: Bearer <device_token>. Response signed envelope (always200 for valid device); unauthorized/revoked device401. At most one pending poll; nominal30s, exponential bounded error backoff, immediate on session startup/enrollment. No cookies and no server-side fetches of user-supplied URLs.
3. POST /api/client/ack same bearer, body {"revision":1,"policy_sha256":"<lowercase sha256 of exact decoded payload bytes>"}. Only after durable verified local settings write succeeds. Backend must validate against its issued/history policy for this user/device/revision, disallow future/bogus ACK. Response {"ok":true}. Track per-device last_seen, applied revision and acked timestamp. Fetch != applied. Re-ACK same current valid policy is idempotent. Never decrease acknowledged revision.
- Client stores URL, pinned public key, device ID/token, revision and exact policy bytes/digest inside encrypted session settings, alongside peers in the same atomic verified write. Existing session remains logged in; no tdata copies/resets/profile migrations. Destroy network work on logout/session teardown; no stale callback may update a different session.
- Native UI: Settings -> Managed allowlist, read-only numeric user ID, enrollment text field, endpoint/identity confirmation, connection/revision/last-success/error status. No ordinary unmanaged edit escape, no self-unenroll for a managed user; current-local-account logout stays. Ordinary onboarding configureAllowlist's already-configured guard remains intact; separate validated managed apply path updates list and fires existing allowlistChanges observer after durable commit. Revalidate active direct/group calls, UI history/dialog visibility and authorization immediately on revocation. Revocation must affect pending allowed-content work too; inspect existing observers rather than assume.

## Dashboard/auth scope
- Owner principal8683512953, multiple scoped head principals identified by numeric Telegram IDs (usernames display only), persistent database. Owner-only head creation/deactivation/user assignments. Heads can only see/edit/invite users assigned to them; all CRUD, audit/status, enroll/revocation routes enforce scope server-side. No auto-owner on first public login; no role self-assignment; owner cannot accidentally disable the last owner. Browser clients cannot fabricate applied status.
- Implement Telegram Login Widget verification if configured with bot token: official HMAC SHA256, constant time, strict fields/IDs/auth_date freshness, fresh server session cookie. Username never authorization. Domain setup with BotFather is a separate owner operation; do not modify any bot or use personal Telegram.
- Provide usable temporary owner bootstrap authentication without pretending Telegram SSO: local CLI mints expiring single-use owner access codes into an explicit0600 file, hashed DB only. No stdout token, query-string token, public bootstrap creation endpoint, hardcoded password, demo auth or unattended auto-login. After claim use secure HttpOnly SameSite=Strict session cookies and CSRF. Owner may mint recovery code locally; document. Additional heads normally use configured Telegram login.
- Browser writes require exact configured Origin plus session CSRF, JSON content types, strict bounded bodies and rate limits. No wildcard CORS. Public URL determines Secure cookies; HTTP allowed only explicit loopback local development. Trusted-host checks for configured public host/loopback. Backend return generic auth errors and safe errors; no tracebacks/secrets. No payload/token HTTP logging. Authenticated data and APIs no-store.
- Dashboard: calm polished blue/slate, responsive desktop/mobile, visible Allowgram branding. Sidebar Users / Heads(owner only) / Activity. Searchable users, initial empty state (no fake seeded production data), per-user contacts/group list + add/remove, revision compare-and-swap conflict handling, save diff/confirm including explicit deny-all empty list. Assigned heads and invitation management. Pending sync vs Applied vs Offline based on individual device ACK, not on fetch or wall-clock guesses. Friendly recoverable errors with edits preserved. Disabled feature/SSO setup prerequisites labeled truthfully.
- Privacy: only managed identity, peer IDs/labels and audit/status. No Telegram messages, authentication keys, contact-book scraping, Google credentials or account session transfer.
